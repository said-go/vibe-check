# VibeCheck Backend

Go API для приёма фото, извлечения признаков одежды через Yandex AI Studio и детерминированного расчёта результата. Backend раздаёт `dist/` на `/` и API на `/api`.

## Запуск

Из каталога `backend/` выполните `go run ./cmd/api`, предварительно задав `YANDEX_API_KEY` и `YANDEX_FOLDER_ID` в окружении. Без них development сервер запускается для проверки интерфейса, а обычный анализ возвращает `503 ai_unavailable`. В production отсутствие реквизитов блокирует запуск, кроме явно настроенного режима с непустым приватным файлом результатов.

`GET /api/healthz` показывает, что процесс жив. `GET /api/readyz` проверяет наличие конфигурации AI и доступность опционального Redis через PING без расходования квоты. Ответ содержит `ai_available`, `presets_available`, `shared_budget_configured`, `shared_budget_available`. При сбое Redis AI недоступен, но приватные результаты сохраняют готовность; если нет ни одного доступного пути, возвращается 503. Проверка не подтверждает действительность AI-ключа, права Redis на Lua или остаток квоты. При размещении в Yandex Serverless Containers сервер слушает порт из `PORT`; явный `HTTP_ADDRESS` имеет приоритет.

```text
GET  /api/healthz
GET  /api/readyz
POST /api/v1/analyses
```

`POST /api/v1/analyses` принимает ровно одно поле `image` (JPEG/PNG, 128×128 или больше, до 20 мегапикселей) и ровно одно `privacy_consent=true`. Дубли полей отклоняются. Максимальный размер запроса 10 МБ. PWA уменьшает выбранное фото до 1600 пикселей по длинной стороне и сжимает в JPEG перед отправкой. Сервер проверяет и повторно кодирует его без EXIF; наш сервер не сохраняет изображение.

PWA передаёт `Idempotency-Key`, который остаётся прежним при повторе одного фото. Успешный результат и SHA-256 очищенного JPEG хранятся до 10 минут в памяти процесса, исходное фото в кеш не попадает. Повтор не вызывает AI и возвращает тот же `analysis_id`; тот же ключ с другим фото получает 409. После рестарта, на другой реплике или после сетевого таймаута у провайдера гарантии единственного платного вызова нет.

PWA также передаёт `X-Original-Image-SHA256` для точного совпадения с двумя согласованными снимками. Сервер сверяет отпечаток с визуальным признаком очищенного фото и возвращает заданный результат без вызова AI. Этот заголовок сам по себе не выбирает результат: чужое фото с подставленным отпечатком идёт обычным путём анализа.

| `YANDEX_MODEL` | `qwen3.6-35b-a3b` |
| `YANDEX_BASE_URL` | `https://ai.api.cloud.yandex.net/v1` |
| `YANDEX_TIMEOUT` | `90s` |

Альтернативный провайдер `AI_PROVIDER=openai` использует `OPENAI_API_KEY`, `OPENAI_MODEL`, `OPENAI_BASE_URL` и `OPENAI_TIMEOUT`. Секреты держите в окружении хостинга, не в Git.

Лимиты возвращают 429 и `Retry-After`. Каждый HTTP-вызов провайдера, включая повтор после некорректного JSON, расходует отдельную единицу часового и клиентского лимита. В журнал `provider_attempt` попадают номер попытки, длительность, HTTP-статус и токены, если провайдер их вернул; фото, ключи и текст ответа туда не входят. Число токенов не является расчётом стоимости в рублях. По умолчанию адрес клиента берётся из соединения, X-Forwarded-For игнорируется. TRUSTED_PROXY_CIDRS позволяет явно задать узкую CIDR-allowlist прокси; цепочка XFF проверяется справа налево. Настройку нужно сверить с реальным облачным прокси (см. инструкцию развёртывания). Лимиты хранятся в памяти одного экземпляра, поэтому при масштабировании для общего бюджета нужен gateway или общий rate limiter.

Весь AI-анализ ограничен 110 секундами, включая повтор. Повтор некорректного ответа допускается один раз и только если осталось хотя бы 15 секунд. Таймаут отдельного HTTP-вызова по умолчанию 90 секунд.

Для Yandex API ключу нужен scope `yc.ai.foundationModels.execute`, а сервисному аккаунту роль `ai.languageModels.user` для каталога. Подробнее в [документации Yandex AI Studio](https://aistudio.yandex.ru/en/docs/ai-studio/operations/generation/multimodels-request).

Строгий контракт признаков: [openapi/ai-features.schema.json](openapi/ai-features.schema.json). Он не содержит национальности, религии, привлекательности, здоровья и иных чувствительных выводов. HTTP контракт: [openapi/openapi.yaml](openapi/openapi.yaml).

Для Qwen3.6 запрос использует JSON-режим с небольшим бюджетом рассуждения. Сервер проверяет все обязательные поля и диапазоны чисел после ответа модели. Кадр с видимой частью одежды получает предварительную оценку; качество фото не входит напрямую в балл стиля. Если модель видит не одного человека, возвращает уверенность ниже 20 или не находит признаков стиля, сервер отдаёт `low_confidence` без категории, уровня и оценки. Без видимой одежды допустим только игровой портретный вердикт по подтверждённой гримасе, жесту, улыбке либо сочетанию тюбетейки с бородой. Эти пороги требуют дальнейшей проверки на согласованном наборе фотографий.

В результате `explanations` содержит до трёх причин выбора категории по реальным входным признакам (для ручных исключений поле может отсутствовать). `provisional` и `assessment_note` передают ограничения кадра отдельно от шутки. При `assessment_scope: portrait` одежда не оценивалась: нули в `score` и `metrics` — технические значения совместимости, интерфейс обязан скрывать их, уровень и второй стиль пустые. Подробные правила — в `docs/SCORING_REVIEW.md`.

## Проверка

### Офлайн-проверка правил на сохранённых признаках

Из `backend/`: `go run ./cmd/evaluate -input internal/evaluation/testdata/synthetic.json`.
Для сохранённых по одному результатов: `go run ./cmd/evaluate -input-dir private/run-001 -expected-count 20 -json`. Выберите ровно один из `-input` и `-input-dir`. Каталог читается без рекурсии, JSON-файлы обрабатываются по имени; не-JSON файлы игнорируются. Пустой/недоступный каталог, повреждённый JSON, смешение видов наборов и повторяющиеся ID приводят к коду 2, а не к частичному успешному отчёту. Символические ссылки и каталоги с расширением JSON не принимаются. Общий размер ограничен 8 МиБ и 10 000 случаями.

`-expected-count` задаёт ожидаемое число случаев от 1 до 10 000. Полнота (`coverage_status`, `expected_count`, `missing_count`) отделена от совпадений вердиктов: даже 2 правильных результата из ожидаемых 3 дают `incomplete` и код 1. Невозможное число меньше загруженного набора даёт код 2. Без флага полнота обозначается `unknown`, ожидаемое и недостающее число — `null`. Равенство количества не подтверждает правильность выбранных ID: их нужно сверять с исходным манифестом. Эти показатели описывают проверку сохранённых признаков, а не точность распознавания фотографий AI.

Разные запуски сборщика могут снова использовать `case-0001`, поэтому оценивайте их отдельно: дубли не перенумеровываются автоматически. Каталог checkpoint-файлов может быть неполным после ошибки сбора; инструмент оценивает только присутствующие записи и не знает полного числа запланированных фото. Такой отчёт нельзя выдавать за результат полного набора. Это позволяет осмотреть сохранённую часть после сбоя; не используйте пустой stdout неудачного сбора как полный dataset.
Добавьте `-json` для машиночитаемого отчёта. Команда не отправляет запросы AI, не принимает фотографии и не читает `.env`. Она вызывает настоящий Scoring Engine и выводит совпадения, ошибки по каждому случаю и таблицу «ожидалось → получилось». Код завершения собранной команды: 0 — все ожидания совпали, 1 — есть ошибки/невалидные признаки, 2 — ошибка входного файла. `go run` может оборачивать ненулевой код процесса.

Формат примера: `kind` (`synthetic` или `reviewed_features`), список `cases`; в каждом случае уникальный `id`, полный контракт `features`, `expected.status`, `expected.category`. Для `low_confidence` категория пустая и требуется `expected.reason`. Неизвестные поля и некорректные ожидания отклоняются. Вход ограничен 8 МиБ и 10 000 случаев.

Для смешанного вердикта задайте `expected.components` — ровно два разных кода в порядке приоритета, первый совпадает с `expected.category`. Например: `{"status":"completed","category":"action_hero","components":["action_hero","muscular"]}`. Отсутствующее поле или пустой массив означает **одиночную** категорию: обычный `action_hero` больше не засчитывает смешанный `action_hero+muscular`. Для `low_confidence` компоненты запрещены. Коды имеют формат `[a-z][a-z0-9_]{0,63}`; дубли, неверный порядок ведущего кода и списки другой длины отклоняются. Те же правила действуют в манифесте сборщика фото.

Отчёт сохраняет `actual.components`, перечисляет `missing_components` и `unexpected_components`; `component_order_mismatch` отмечает правильный набор в неверном порядке. Таблица ошибок показывает полный смешанный вердикт, а CLI завершает работу с кодом 1 при несовпадении любой части.

Пятнадцать включённых примеров — **синтетические регрессии правил, не замер точности распознавания фото**. Они включают одиночные и смешанные категории, портрет, неполные признаки и границу смешивания двух стилей (разница 15/16 баллов). Для следующего этапа нужны независимо согласованные ожидания и признаки, полученные на репрезентативном наборе фотографий. Используйте обезличенные ID; реальные наборы и отчёты храните в игнорируемом `backend/private/`, не добавляйте фото или персональные сведения в fixtures. Проверка сохранённых признаков отделяет ошибки scoring от ошибок распознавания, но сама по себе не измеряет качество всей AI-цепочки.

```bash
go test ./...
go vet ./...
```

Инструкция по размещению: [../docs/DEPLOY_YANDEX.md](../docs/DEPLOY_YANDEX.md).

## Сбор признаков из набора фото (платный, только явно)

`collect-evaluation` читает локальный JSON-манифест с заранее выбранными ожидаемыми результатами. Путь каждого снимка разрешается относительно манифеста; поддерживаются JPEG/PNG до 10 МиБ и 20 Мп. Рекомендуемое место для манифеста и результата — `backend/private/`, исключённое из Git и Docker.

Пример приватного манифеста:

```json
{"cases":[{"path":"photos/example.jpg","expected":{"status":"completed","category":"goth"}}]}
```

Из `backend/`, после установки AI-реквизитов в окружение процесса:

```powershell
go run ./cmd/collect-evaluation -input private/manifest.json -output-dir private/run-001 -allow-paid -max-calls 10 > private/features.json
go run ./cmd/evaluate -input private/features.json
```

Без `-allow-paid` команда отказывает до чтения манифеста/настроек и ничего не отправляет. Флаг подтверждает разрешение отправить все перечисленные снимки настроенному AI и оплатить попытки. Лимит 1–100 считает HTTP-попытки, включая повтор провайдера; весь запуск ограничен 30 минутами, Ctrl+C отменяет работу. Приватные заданные ответы приложения не используются. `.env` автоматически не загружается, ключи не передавайте в аргументах.

В stdout сохраняются только признаки, ожидаемые результаты и сгенерированные номера `case-0001`; пути и фото не включаются. Храните файл приватно: признаки всё ещё относятся к снимкам людей. `kind=reviewed_features` означает ожидания из выбранного вами манифеста, а не ручную проверку каждого признака AI. До первого AI-вызова проверяются все изображения по очереди без хранения всего набора в памяти; перед отправкой повторно проверяется отпечаток файла. Требуется новый каталог -output-dir: существующий каталог не перезаписывается. После каждого успешного ответа отдельный case-XXXX.json записывается и синхронизируется с диском; каждый файл можно передать evaluate. При ошибке команда останавливается, предыдущие файлы сохраняются; ошибка записи прекращает дальнейшие платные вызовы. Полный dataset в stdout появляется только при успехе. Автоматического resume нет: повтор всего манифеста снова оплачивает уже обработанные снимки; для продолжения подготовьте манифест только оставшихся случаев в новом каталоге. Не включайте частичный сбор в отчёт точности полного набора. Не запускайте следующий evaluate после неудачного сбора. Эта утилита подготовлена и проверена на mock-провайдере; качество на реальной выборке ещё не измерено.

## Отчёт по попыткам и токенам

Из `backend/`: `go run ./cmd/usage-report -input private/server.jsonl`. Без `-input` команда читает JSON-lines из stdin. Это локальная обработка журналов, без сети и вызовов AI.

JSON-отчёт содержит количество попыток, группировку по провайдеру и исходу, суммы входных/выходных/общих токенов и `unknown_usage`. Явные нулевые токены отличаются от отсутствующего usage. Суммы включают только известные значения; это не расчёт стоимости в рублях. Другие сообщения журнала пропускаются. Повторно импортированные строки считаются повторно: передавайте один непересекающийся набор журналов.

Некорректные строки учитываются в `invalid_lines`; строка свыше 1 МиБ или ошибка чтения останавливает разбор с `input_incomplete=true`. Код выхода 0 означает обработку без повреждённых записей, 1 — частичный отчёт, 2 — ошибку аргументов/файла/вывода. Сырые строки, идентификаторы запросов, IP, пути и секреты не выводятся. Храните исходные журналы в игнорируемом `backend/private/`; они могут содержать личные данные из других источников.

### Оценочная стоимость по явно заданному тарифу

`go run ./cmd/usage-report -input private/server.jsonl -tariff private/tariff.json -assume-model test-model`

Ниже только синтетический пример формата, **не действующие цены**:

```json
{"version":"synthetic-example-v1","currency":"RUB","rates":[{"provider":"yandex","model":"test-model","input_rub_per_million":"1.25","output_rub_per_million":"2.50"}]}
```

Перед реальным использованием вручную внесите проверенные ставки для своей модели и версию тарифа. Ставки задаются десятичными строками рублей за миллион входных/выходных токенов (до 6 знаков после точки). Расчёт использует точную рациональную арифметику и выводит 12 десятичных знаков, без ошибок float. Версия и допущение о модели включены в отчёт.

`-assume-model` обязателен: серверные журналы пока не содержат модель, поэтому оператор явно подтверждает, что весь входной журнал относится к одной модели. Не объединяйте разные модели. Если импортированный журнал всё же содержит `model` и он не совпадает с допущением, оценка отклоняется. Неизвестный usage или отсутствие ставки для провайдера дают `unpriced_attempts`, `partial=true` и код 1; они не считаются бесплатными. `known_cost_rub` — только сумма известных частей по заданным ставкам, а не счёт провайдера: скидки, отдельные категории токенов и другие сборы не моделируются. Без `-tariff` денежная оценка не добавляется. Дубликаты ставок/JSON-полей и отрицательные ставки отвергаются.


Обновление отчёта: пользователь видит только одну категорию; прежний уровень (`level_title`) не отображается в отчёте, истории и карточке. Общие баллы подписаны «Оценка одежды: …/100». Старые записи истории отображаются по тем же правилам. Для «Пупсика» нужны оба признака `gentle_smile_visible` и `relaxed_head_tilt_visible` (лёгкий наклон головы вместе с расслабленными бровями). Одной улыбки недостаточно. Отсутствующий новый признак считается ложным; доброта, характер и «жалкий вид» не распознаются.


Смешанные вердикты возвращают необязательный массив `components` из двух категорий; отображается единый `primary_category.title`. Добавлены видимые признаки `beard_absent_visible`, `muscular_visible`, `non_muscular_visible`. Неизвестность оставляет их false, противоречивые пары отклоняются. Правила и пороги описаны в `docs/SCORING_REVIEW.md`.


`action_hero` («Герой боевика») — общий шуточный кинообраз по сочетанию `short_hair_or_bald_visible`, `beard_visible`, `head_scar_visible`; поддерживает `components` и портретный режим. Новые поля передаются в обоих AI-контрактах, старые ответы без них не запускают категорию. Полные условия и приоритет описаны в SCORING_REVIEW.

## Локальная диагностика анализа

Из корня проекта: `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-local.ps1 -Diagnostics`. Откройте `http://localhost:8080`, выберите фото и включите «Показать диагностику этого запроса — только локально» перед анализом. Под результатом или отказом появится раскрываемый блок: признаки AI, баллы кандидатов, условия специальных категорий и выбранный результат. Неподтверждённый признак может быть неразличим на снимке; это не доказательство его отсутствия.

Все числовые и логические признаки показаны с русскими названиями, включая сигналы стилей. «Не подтверждено» не означает доказанного отсутствия. Баллы кандидатов показывают соответствие категории, а не вероятность; подтверждённое сочетание ещё не гарантирует выбор из-за приоритетов и ограничений качества. Бонус Нефору отображается отдельно от выбранных категорий. Поле `decision_reasons` показывает выполненные шаги выбора: лидера и ближайшего кандидата с баллами, изменения приоритета, отказы при смешивании, добавление второй части и возможную отмену вердикта из-за недостаточности данных. Эти шаги получены повторным выполнением того же детерминированного scoring-кода без вызова AI; они не входят в обычный результат и историю. Проверка смешивания останавливается после первого подходящего кандидата. Для старых ответов без этих данных интерфейс сообщает, что показаны не все этапы. Автотест сверяет словари интерфейса с Go-контрактом, чтобы новые признаки не пропадали без перевода.

Режим требует development и привязывает сервер к `127.0.0.1:8080`. По умолчанию он выключен; запросы через прокси или с посторонним Origin отклоняются. Данные не входят в историю и карточку, не содержат фото, ключи или сырой ответ провайдера. Для заранее заданного ответа AI не запускается. Если исходный запрос выполнен без диагностики, повтор из кеша не запускает AI заново: для новых признаков нужно выбрать фото заново, что расходует лимит AI.

Баллы считаются целочисленно с округлением половины вверх. Это устраняет случайную разницу округления для одинаковых признаков, но не гарантирует одинаковый ответ внешней AI-модели при повторной отправке фотографии.
