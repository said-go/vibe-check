# Обслуживание публичной beta

## Откат без сброса бюджета

Локальный `backend/private/cloud-release-state.json` содержит только ID ресурсов, ссылки на версии секрета и параметры релиза. Значения ключей и фотографии туда не входят; файл исключён из Git. Сохраните его копию перед обновлением: старый digest должен оставаться в Registry.

Сначала покажите план и сравните действующую конфигурацию с сохранённой:

```powershell
$env:PATH = 'C:\Users\Uzver\yandex-cloud\bin;' + $env:PATH
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/rollback-yandex.ps1 `
  -StateFile backend/private/cloud-release-state.json `
  -ImageDigest sha256:<проверенный-digest> -CheckCurrent
```

`-CheckCurrent` только читает активную ревизию. Без него и без `-Apply` облачных вызовов нет. Для фактического возврата замените `-CheckCurrent` на `-Apply`, затем выполните `scripts/smoke-yandex.ps1 -BaseUrl <HTTPS-адрес>`.

Wrapper сохраняет YDB DSN, тот же ключ счётчика, часовой/месячный лимиты и ссылки Lockbox. Он останавливается при расхождении активной конфигурации: нельзя случайно вернуть стандартные 30 попыток/час, отключить YDB или заменить секрет. Поддерживается текущий профиль beta — 1 vCPU, 1 ГБ, 180 секунд, concurrency 2, максимум 1 экземпляр в зоне, без прогретых экземпляров и пользовательской сети. При изменении профиля сначала обновите инструкцию и проверки. Это возврат образа; данные YDB и публичный доступ не изменяются. Команду `init-ydb-budget` при откате запускать не нужно.

После таймаута CLI сначала прочитайте состояние ревизий: удалённая операция могла завершиться. Не повторяйте изменение вслепую. Конкурирующие deploy-команды не запускайте.

На 15 ноября 2026 wrapper проверен на активной ревизии в режиме чтения; 20 регрессионных проверок покрывают план, точные лимиты 5/100, смену секрета/ключа/профиля, metadata/logging-настройки и ошибочные аргументы. Они включены в общий `test-deployment.ps1`, поэтому выполняются в preflight и CI. Реальный откат отмечается отдельно после выполнения.

## Проверка журналов

15 ноября 2026 повторная диагностика дала `Unavailable` через `yc logging group list` и HTTP 503 через официальный REST `GET https://logging.api.cloud.yandex.net/logging/v1/logGroups`. Это подтверждает недоступность API, а не ошибку имени группы в локальной команде. Содержимое production-журналов не удалось прочитать, поэтому аудит не отмечен выполненным. Создание другой группы или смена runtime-прав без новых доказательств не требуется.

Когда API восстановится, прочитайте ограниченное окно записей только контейнера (`yc logging read --resource-ids <container-id> --since 1h --limit 100 --format json`). Не печатайте сырые журналы в общий чат и не сохраняйте их в репозиторий. Проверяйте в памяти совпадение с текущим API-ключом, `Authorization`, `data:image/`, `base64,` и содержимым multipart; выдавайте только количество записей и флаги обнаружения. Отсутствие совпадения в выборке не доказывает безопасность всей истории.

В исходном коде прикладные события ограничены статусами, временем и токенами; ошибки провайдера не логируют тело ответа. Факт отсутствия секретов в настоящих облачных журналах всё ещё нужно подтвердить.

Источники: [чтение Cloud Logging](https://yandex.cloud/en/docs/logging/operations/read-logs), [официальный REST endpoint](https://yandex.cloud/en/docs/logging/api-ref/).
