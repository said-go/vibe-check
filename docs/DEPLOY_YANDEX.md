# Развёртывание ВАЙБЧЕК в Yandex Cloud

Для рабочего AI-сценария разверните **весь проект одним контейнером**: Go сервер раздаёт PWA на `/` и API на `/api`. Это сохраняет один HTTPS origin для камеры, Service Worker и загрузки фото. Опубликованный статический Sites остаётся демонстрацией интерфейса до переключения пользователей на адрес контейнера.

Потребуются каталог Yandex Cloud с биллингом, Yandex Container Registry, Serverless Containers, сервисный аккаунт с доступом к AI Studio и секрет в Lockbox. Локально нужен Docker; для командного способа также `yc` CLI. Текущая среда разработки не имеет `yc` CLI или работающего Docker daemon, поэтому эта инструкция пока не является подтверждением живого запуска.

## 0. Проверить локальную готовность

Из корня проекта на Windows запустите `powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/preflight.ps1`. Скрипт выполняет Go тесты, `go vet`, проверку синтаксиса, согласованности ресурсов и поведения PWA; сообщает, доступны ли Docker daemon и `yc`. Проверка Docker ограничена по времени. Скрипт не читает секреты и не создаёт облачные ресурсы. После запуска Docker можно добавить `-BuildImage`, чтобы проверить локальную сборку; `-RequireCloudTools` требует готового Docker daemon и установленного `yc`.

Сценарий `scripts/deploy-yandex.ps1` принимает только ID ресурсов, проверяет их формат и по умолчанию показывает план без облачных операций. Запуск с `-Apply` требует чистое Git-дерево, работающий Docker, настроенную авторизацию Docker в Container Registry и `yc` с правами на контейнер. Он собирает образ с полным SHA коммита, отправляет его в Registry и создаёт новую ревизию существующего контейнера. Он не создаёт ресурсы, не открывает публичный доступ и не читает значение ключа из Lockbox.

```powershell
pwsh -NoProfile -File scripts/deploy-yandex.ps1 `
  -FolderId <folder-id> -RegistryId <registry-id> -ContainerId <container-id> `
  -ServiceAccountId <service-account-id> -SecretId <lockbox-secret-id> `
  -SecretVersionId <lockbox-version-id>
# Повторите с -Apply после проверки плана и доступа.
```

## 1. Подготовить доступ

Сценарии проверяются локально командой `powershell.exe -NoProfile -File scripts/test-deployment.ps1` (или `pwsh -NoProfile -File scripts/test-deployment.ps1` на Linux). Проверки подменяют Git, Docker, yc и HTTP; облачные вызовы и отправка фото не выполняются. Проверяются режим плана, запрет грязного рабочего дерева, неверные ID/URL, отсутствие AI, неверный Content-Type ресурса, ошибка и таймаут внешнего процесса.

В режиме `-Apply` команды ограничены по времени: Docker info — 15 секунд, чтение контейнера — 60, сборка — 900, push — 600, публикация ревизии — 300. После таймаута процесс CLI завершается, но удалённая операция могла продолжиться: проверьте состояние Registry/ревизии перед повторным запуском. Вывод CLI с возможными диагностическими данными не печатается; скрипт сообщает имя команды и код завершения.

Создайте сервисный аккаунт для контейнера. Дайте ему `container-registry.images.puller` на registry, `ai.languageModels.user` на каталог и `lockbox.payloadViewer` на конкретный секрет. Если секрет защищён пользовательским KMS ключом, потребуется и `kms.keys.encrypterDecrypter` на ключ. Для создания ревизии вызывающему пользователю нужна роль `iam.serviceAccounts.user` на сервисном аккаунте; для отправки образа в Registry — `container-registry.images.pusher` на registry или repository. Создайте API-ключ с областью `yc.ai.foundationModels.execute`, сохраните его в Yandex Lockbox под ключом `YANDEX_API_KEY`. Ключ не добавляйте в GitHub, Dockerfile или командную строку.

## 2. Собрать образ

Создайте Container Registry и настройте официальный Docker credential helper командой `yc container registry configure-docker`. Из корня репозитория соберите образ по `Dockerfile`, пометьте адресом вашего Yandex Container Registry и отправьте туда. Деплойте конкретный тег или digest, связанный с Git commit; не используйте плавающий `latest` для проверки релиза.

```text
docker build --platform linux/amd64 -t cr.yandex/<registry-id>/vibe-check:<git-sha> .
docker push cr.yandex/<registry-id>/vibe-check:<git-sha>
```

## 3. Создать контейнер и ревизию

Создайте Serverless Container `vibe-check`. В ревизии укажите образ, сервисный аккаунт, таймаут выполнения 180 секунд, память и ограничения параллельных запросов. У приложения таймаут приёма фото составляет 30 секунд, запроса к AI — 90 секунд, HTTP запись ограничена 150 секундами; дополнительное время платформы покрывает запуск контейнера. Приложение слушает переменную `PORT`, которую выставляет платформа. Задайте обычные переменные:
Для анализа снимков размером до 20 мегапикселей выделите как минимум 512 МБ памяти, предпочтительно 1 ГБ: декодирование и очистка кадра создают несколько копий пикселей в памяти.

У Serverless Containers жёсткий предел входящего HTTP-запроса **3,5 МБ вместе с заголовками**. Браузер может открыть исходное фото до 25 МБ локально, но перед отправкой сжимает JPEG до **2,5 МиБ**. Серверный лимит в 10 МБ не отменяет ограничение платформы: запрос большего размера будет отклонён ещё до приложения.

```text
APP_ENV=production
AI_PROVIDER=yandex
YANDEX_FOLDER_ID=<folder-id>
YANDEX_MODEL=qwen3.6-35b-a3b
FRONTEND_DIR=/app/dist
ANALYSES_PER_HOUR=30
ANALYSES_PER_CLIENT_MINUTE=3
MAX_CONCURRENT_ANALYSES=2
```

Привяжите `YANDEX_API_KEY` из Lockbox как переменную окружения ревизии. После ротации ключа создавайте новую ревизию. Для браузерного доступа контейнеру потребуется публичный HTTPS вызов; это решение применяйте только после включения лимитов запросов и оценки расходов.

При работе через CLI команда создания контейнера — `yc serverless container create --name vibe-check`. Для ревизии используйте `yc serverless container revision deploy` с `--container-name`, `--image`, `--service-account-id`, `--execution-timeout 180s`, `--environment` для перечисленных выше открытых значений и `--secret environment-variable=YANDEX_API_KEY,id=<secret-id>,version-id=<version-id>,key=YANDEX_API_KEY`. Секретные значения в `--environment` не передавайте. Точные параметры CLI сверяйте с [документацией ревизий](https://yandex.cloud/en/docs/serverless-containers/operations/manage-revision) и [Lockbox](https://yandex.cloud/en/docs/lockbox/operations/serverless/containers).

Скрипт задаёт максимум один экземпляр **на зону**, поэтому суммарный расход может расти при запуске в нескольких зонах. Его лимиты в памяти также действуют отдельно на каждом экземпляре. Перед публичным доступом настройте бюджет и проверьте доступные ограничения в облаке.

Встроенные лимиты считают каждый HTTP-вызов AI, включая повтор после некорректного ответа, и работают в памяти одного экземпляра. Если платформа запускает несколько экземпляров, общий расход может превышать `ANALYSES_PER_HOUR`; ограничьте масштабирование или настройте внешний gateway с общим лимитом перед открытым релизом. Весь анализ ограничен 110 секундами, отдельный вызов по умолчанию — 90 секундами. Метрики `provider_attempt` помогают проверять количество попыток и возвращённые провайдером токены, но не заменяют облачный бюджет.

Приватные заранее заданные результаты исключены из Git и Docker context. Для облака их нужно отдельно доставить как защищённый файл и задать `PHOTO_PRESETS_FILE`; стандартный deploy-скрипт этого не делает. Без файла доступен обычный AI-анализ. Smoke-проверка требует `ai_available=true`, поэтому режим только с приватными результатами не считается готовым облачным AI-релизом.

## 4. Проверить релиз

Smoke дополнительно сверяет SHA-256 содержимого JS/CSS с хешем в имени файла (CRLF приводится к LF, как при сборке), доступность PNG-иконок и совпадение списка APP_SHELL в Service Worker со ссылками HTML и манифеста. Пути иконок допускаются только внутри `/icons/`, без внешних URL и переходов каталогов. Это выявляет смешанные версии и подменённые страницы ошибок; готовность AI по-прежнему требует отдельного реального сценария с фото.

### Идентификация клиента за прокси

По умолчанию клиентский лимит использует адрес непосредственного соединения и игнорирует `X-Forwarded-For`. Если перед сервером есть управляемый reverse proxy, можно явно задать `TRUSTED_PROXY_CIDRS`: список его IPv4/IPv6 CIDR через запятую. Не включайте эту настройку, пока не проверены реальные адреса прокси и его правило обработки заголовка: он должен перезаписывать XFF адресом клиента либо дописывать настоящий адрес отправителя справа. Адреса здесь намеренно не предустановлены для Yandex Cloud.

Сервер принимает XFF только от доверенного непосредственного узла, разбирает цепочку справа налево и останавливается на первом недоверенном адресе. Произвольный левый адрес не позволяет обойти лимит. Дубли заголовка, некорректный IP, IPv6 zone, цепочка длиннее 32 адресов или заголовок больше 2048 байт приводят к использованию адреса соединения. CIDR по умолчанию `/0` и некорректная конфигурация блокируют запуск. Используйте максимально узкую allowlist; широкая доверенная сеть может включить посторонние узлы.

Это разделяет клиентские лимиты за проверенным прокси, но не объединяет бюджет разных экземпляров. Общий облачный rate limiter и проверка поведения реального gateway остаются отдельными задачами.

Пока контейнер закрыт, проверьте `https://<container-id>.containers.yandexcloud.net/api/healthz` и `/api/readyz` через авторизованный HTTP клиент с IAM токеном по [инструкции Yandex Cloud](https://yandex.cloud/en/docs/serverless-containers/operations/invoke). Браузерная PWA на этом этапе не может вызвать закрытый контейнер без IAM токена. Проверьте журналы на отсутствие изображения, API-ключа и тела запроса.

После открытия публичного доступа для проверок без отправки фото запустите `pwsh -NoProfile -File scripts/smoke-yandex.ps1 -BaseUrl https://<container-id>.containers.yandexcloud.net/`. Он требует ответы 200 от `healthz`, `readyz`, главной страницы и PWA-манифеста. Затем через PWA отправьте тестовое фото после явного согласия и убедитесь, что появляется результат либо понятная ошибка низкой уверенности. Для проверки лимита отправьте серию запросов и убедитесь, что сервер возвращает 429 до обращения к AI. Скрипт проверяет обычный публичный HTTPS origin. Для локального Go сервера допускается `-AllowHttp`.

Когда контейнер пройдёт проверки и лимит расходов будет настроен для публичного трафика, разрешите вызов без IAM токена через `yc serverless container allow-unauthenticated-invoke vibe-check`. После живой проверки укажите адрес контейнера как основной URL проекта. Статический Sites не проксирует запросы к Go серверу и не является полноценным релизом анализа.

## Возврат к прежнему образу

`scripts/deploy-yandex.ps1 -ImageDigest sha256:<64 строчных hex-символа>` создаёт новую ревизию из существующего образа `cr.yandex/<RegistryId>/vibe-check@sha256:...`. Без `-Apply` показывает только план. Этот режим не собирает и не отправляет образ, не требует Docker или чистого Git-дерева; для применения нужен `yc`. Произвольные URL, другие репозитории, теги `latest` и SHA-коммита вместо digest отклоняются.

Перед обновлением сохраните digest известного рабочего образа из [информации о ревизии](https://yandex.cloud/en/docs/serverless-containers/operations/revision-info) и значения её настроек. В вызове оставьте обязательные ID каталога, registry, контейнера, сервисного аккаунта и версии AI-секрета. Если приложение использует Redis, повторно передайте оба RedisSecret ID и настройки общего бюджета. Значения секретов не передаются.

Это **возврат версии образа**, а не автоматическое восстановление конфигурации старой ревизии: окружение и лимиты создаются по текущему скрипту и явно указанным параметрам; отсутствие Redis-параметров отключает его привязку. Сверьте модель, лимиты, сеть и версии секретов до `-Apply`. Скрипт не меняет публичный доступ и не откатывает данные Redis или другие внешние данные. Образ должен оставаться в Registry и быть доступен сервисному аккаунту.

После применения выполните smoke и проверку анализа. Если команда завершилась по таймауту, сначала проверьте состояние ревизии, прежде чем повторять действие. Реальный облачный возврат пока не выполнен; локальные тесты проверяют точный digest, отсутствие build/push и остановку при ошибке поиска контейнера.

## Общий бюджет AI нескольких экземпляров

Опционально задайте `REDIS_BUDGET_URL=rediss://...`, `REDIS_BUDGET_KEY=vibe-check:provider-budget` и `SHARED_ANALYSES_PER_HOUR=30`. URL с паролем — секрет, передавайте через защищённое окружение/Lockbox. В production нужен TLS; для локальных тестов допустим redis://. Все экземпляры одного приложения должны использовать один Redis, одну базу, ключ и одинаковый лимит. Разные окружения используют разные ключи.

Каждая попытка HTTP к AI резервирует единицу общего бюджета атомарным Lua-скриптом Redis; окно длится 3600 секунд с первого вызова и использует TTL Redis, а не часы контейнеров. Повтор после невалидного JSON также расходует единицу. Приватные результаты и успешные idempotency-повторы не обращаются к общему бюджету. При исчерпании возвращается 429/Retry-After, при недоступности Redis — 503 без вызова AI. Автоматический повтор Redis-команды отключён: потерянный ответ мог уже списать единицу.

Локальные клиентские/часовые/параллельные лимиты сохраняются дополнительно. Локальный бюджет может консервативно списаться даже при отказе Redis. Лимит измеряет попытки, а не рубли, и не заменяет облачные ограничения расходов. До публичного релиза нужны Redis без вытеснения бюджетных ключей (`noeviction`), подходящая персистентность/резервирование и проверка отказов: удаление ключа, потеря данных при рестарте или failover сбрасывают счётчик. Скрипт развёртывания Redis не создаёт; доступ и параметры сети нужно настроить отдельно. Опциональная привязка секрета описана ниже.

Локальные тесты используют miniredis, а `REDIS_TEST_URL` включает дополнительный тест конкурентных клиентов с настоящим Redis. Тест создаёт уникальный ключ с TTL один час. Контракт атомарности: [Redis Lua](https://redis.io/docs/latest/develop/interact/programmability/eval-intro/), [INCR rate limiter](https://redis.io/docs/latest/commands/incr/).

### Передача Redis-секрета при развёртывании

Создайте в Lockbox запись `REDIS_BUDGET_URL` со значением `rediss://...` и дайте сервисному аккаунту контейнера доступ к этому секрету. Сам URL с паролем в аргументы скрипта не передаётся. К существующей команде deploy добавьте:

```powershell
-RedisSecretId <redis-secret-id> -RedisSecretVersionId <redis-secret-version-id> `
  -RedisBudgetKey vibe-check:provider-budget -SharedAnalysesPerHour 30
```

Оба ID обязательны вместе; ключ и лимит без них отклоняются. Без этих параметров Redis не включается. Сначала выполните обычный план без `-Apply`; он показывает включение общего бюджета, не читая секрет. При `-Apply` создаётся ревизия с двумя отдельными `--secret`: ключ AI и URL Redis. Повторение флага соответствует [документации передачи нескольких секретов](https://yandex.cloud/en/docs/lockbox/operations/serverless/containers). Скрипт не создаёт Redis, не проверяет пароль и не меняет публичный доступ. До включения трафика проверьте доступность Redis из сети контейнера и одинаковые настройки бюджета на всех экземплярах.
